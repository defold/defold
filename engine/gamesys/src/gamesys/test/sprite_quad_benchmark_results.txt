Decision

The CPU results justify a real-backend quad prototype. For moving, animated
sprites in one batch/pass, compact instances reduce measured CPU preparation
by about 20% at 10,000 and 50,000 sprites. They reduce packing time by about
48% and 45%, respectively. Matrix instances also improve preparation time,
but save much less dynamic data at counts using 16-bit indices.

This is not a GPU result or a whole-game frame-time prediction. Do not switch
the default sprite material based on this benchmark. Next measure actual
driver uploads, vertex processing, fragment work and presentation on desktop
and a mobile/web adapter, with rendered-image parity.

Method

- Real sprite update, transform propagation, animation cache, sorted render
  list, batching, buffer packing and render-object submission.
- Baseline: current optimized quad writer; 4 vertices (24 bytes each) and
  6 indices. Index width changes above 16,384 sprites.
- Matrix: shared unit quad plus 104-byte instance (mat4 + mat3 + float page).
- Compact: shared unit quad plus 64-byte instance (world origin/two XYZ axes,
  affine UV mapping, page), packed into four vec4 attributes.
- Both instance formats fold size/pivot into their geometry transform. They
  are private fixed-layout prototypes, not a public material/API contract.
- Shared quad vertex/index buffers total 44 bytes, uploaded once, excluded
  from the dynamic upload columns. Baseline is unpaged; both prototypes
  include a 4-byte page field, set to zero for this fixture.
- Single texture, alpha blend, four animation frames, all flip combinations,
  off-center pivot, negative scale and a sprite plane rotated in 3D.
- Static: stationary transforms and frozen animation; moving: moving
  transforms and frozen animation; animated: moving transforms and animation.
- Fragmented: 64 synthetic batch keys at distinct depth groups. This models
  batch fragmentation, not the driver cost of changing actual materials.
- Multipass: three draws of the same list, separate buffered backing per pass.
- Null backend: indexed vertex capture is disabled equally in all modes.
  Its usual CPU expansion ignores instance_count and would bias comparison.
  Null draw setup/counters remain; uploaded bytes and bindings are validated.
- prepare_us = measured sprite-pipeline CPU frame time minus measured null
  upload allocation/copy time. It includes update, submission, sorting,
  packing and count-only drawing. Upload time is NOT driver/GPU upload time.
- Three fresh processes per mode/scenario/count, rotating mode order.
  Each process: first rendered frame, 30 warmup frames, 7 samples of 60 frames.
  A setup update precedes the first rendered frame. Cold rows are excluded.
- Summaries are medians of process medians of warm sample means. Different
  columns are summarized independently and need not sum exactly.
- No CPU affinity or clock locking. Run ranges below expose variability.
- Input mutations, construction, validation and logging are outside timings.

Validation

- 135 benchmark invocations passed (3 counts x 5 scenarios x 3 modes x 3 runs).
- Reconstruct every instanced corner/UV and compare with CreateVertexData.
- Check uploaded payloads, shared geometry, instance counts, buffer offsets,
  sorted instance order, draw count and submitted index count.
- Check buffer backing count matches dispatch count in multipass cases.
- Existing SpriteTest.* suite: 20 tests, 2,942 assertions passed.
- This does not validate GPU shaders, transparency compositing or rendering
  on an actual graphics adapter. No slice-9, trimmed geometry, multiple
  textures, arbitrary custom attributes, or production fallback implementation.

in tmp/sprite-quad-benchmark-final/{raw.json,summary.json,summary.txt,*.log}.
