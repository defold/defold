Workload 8

Threaded update

Threaded frame phases and p95

Main thread

  • Starts the frame's four updates. In Defold/Flecs/EnTT it admits queries, submits partition jobs, processes completion callbacks and retries conflicting updates as access becomes available.
  • Prepares incoming resource handles/templates while worker jobs run. This uses prepared input; file I/O is excluded.
  • After every update finishes, removes/replaces mixed content, spawns/despawns enemy waves and releases temporary resources. These structural changes affect the next frame's queries.
  • Validates values, live counts and stale IDs after frame measurement ends.

Worker threads

  • Traverse assigned query partitions. Movement updates Player/Enemy positions from velocity with a 1/64-second timestep.
  • Explosion reads positions and subtracts 25 health inside radius 50; Regenerate adds 0.25 health, capped at 100.
  • Nearby lights reads positions and nested Light color/intensity, then accumulates the distance-weighted contribution. Partition results are combined when the update finishes.
  • Jobs access existing rows. Conflicting updates cannot overlap; additions/removals wait until all workers finish the frame's query work.

Scheduling differences

  • Defold uses caller-owned HJobSystem jobs, query access reservations and 4,096-row ranges.
  • Flecs uses HJobSystem, per-worker cached queries, stages and ecs_worker_iter. The caller resolves conflicts using declared component access and matched tables.
  • Bevy uses unchained systems with Query<&mut T> access, its own scheduler and parallel query iterator.
  • EnTT uses public sparse-pool views and caller-owned jobs. Pool-level conflict checks conservatively serialize Movement and lights.
  • Unity uses Burst IJobChunk.ScheduleParallel and the Jobs worker pool. The caller derives dependency handles from component read/write access in seeded task order. Component-level dependencies conservatively serialize Movement and lights. The main thread prepares content, then polls completion before committing structural changes.

Bevy's coordinator thread

Bevy has an additional persistent coordinator thread that owns the World and runs the Schedule during updates. The main thread prepares content concurrently, then receives World ownership back before spawning or despawning. Component row work runs on the configured worker pool.

The 1/2/4/8-worker labels count row workers. Each backend also has a main thread; Bevy additionally has this coordinator. Coordinator and synchronization overhead are included in frame timing.

Defold/Flecs/EnTT request a 1 µs sleep when polling makes no progress; OS rounding is included. Bevy uses its scheduler's waiting policy. Unity yields with Thread.Sleep(0) until jobs finish, then calls Complete; the main thread does no component row work. Defold prepares borrowed packed-resource handles; the other backends prepare decoded templates. Each run validates values against its actual admitted task order outside timing.

Measurement contract

Method and source data

One representation per library

Standalone cases use one million rows split 10/15/1/24/25/25% across SpotLight, PointLight, Player, Enemy, Pickup and Breakable. Defold uses mutable rows with shared field metadata; Flecs and Bevy use separate components; EnTT uses separate sparse component pools and ordinary views, without owning groups. Unity uses separate IComponentData components in archetype chunks. Light is inline. Public query/get/set APIs traverse data; type/field binding is outside traversal timing.

Unity runs in a standalone macOS arm64 IL2CPP player with Burst AOT, outside the Editor. Its chunk jobs run synchronously for standalone cases; shuffled reads use ComponentLookup. Each sample uses a fresh store. Query and lookup cases run before spawn/despawn. Read/write cases start from original values, with restoration outside timing. Three case queries remain alive for spawn/despawn. Vectors are float32; other numbers are float64. Input generation, caller ID-buffer allocation, setup and validation are outside measurements. Defold creation prepares a shared default and binds native overrides inside timing. Its shuffled reads use typed batch getters; gathering IDs and accumulating returned values are timed.

Timing and memory

Standalone memory covers backend allocations, excluding prepared inputs and caller-owned ID arrays. Threaded memory covers complete frames, including jobs, incoming resources and content changes. All exclude allocator headers, RSS, OS thread stacks and libc/pthread allocations. Defold retains reset defaults; the other measured stores do not. Unity has timing measurements only.
