Query/Setup, field access and row iteration using the public C API from C++.

01 / 08

Create population

Populate a table in the existing store in bulk. This example adds two Enemies; the benchmark compares the AoS and SoA paths across all six types using identical values.

Query/Setup

No query is needed. The application already owns a global store, passed here as store. Call CreateEnemyTable(store) once and check for DATA_RESULT_OK before adding Enemies. The table contains health, velocity and position. offsetof and sizeof describe the native C layout.

C++ · public C API
#include <stddef.h>
#include <dmsdk/data/data.h>

struct Enemy
{
    double      m_Health;
    DataVector3 m_Velocity;
    DataVector3 m_Position;
};

static DataResult CreateEnemyTable(HDataStore store)
{
    DataFieldDesc fields[] = {
        { .m_Field = dmHashString64("health"), .m_Type = DATA_TYPE_NUMBER, .m_Offset = offsetof(Enemy, m_Health) },
        { .m_Field = dmHashString64("velocity"), .m_Type = DATA_TYPE_VECTOR3, .m_Offset = offsetof(Enemy, m_Velocity) },
        { .m_Field = dmHashString64("position"), .m_Type = DATA_TYPE_VECTOR3, .m_Offset = offsetof(Enemy, m_Position) }
    };
    DataTableDesc table = {
        .m_Type = dmHashString64("Enemy"),
        .m_Fields = fields,
        .m_FieldCount = 3,
        .m_RowStride = sizeof(Enemy)
    };
    return DataRegisterTable(store, &table);
}

Population creation · AoS

Pass an array of structures (AoS): each Enemy contains its health, velocity and position. One group is assigned to every added row. Different groups can share the same Enemy table; each row still receives its own DataId.

C++ · public C API
static DataResult CreatePopulationAoS(HDataStore store, DataId out_ids[2])
{
    Enemy enemies[] = {
        { .m_Health = 100.0, .m_Velocity = { .m_Values = { 1.0f, 0.0f, 0.0f } }, .m_Position = { .m_Values = { 10.0f, 0.0f, 0.0f } } },
        { .m_Health = 80.0, .m_Velocity = { .m_Values = { 1.0f, 0.0f, 0.0f } }, .m_Position = { .m_Values = { -20.0f, 0.0f, 5.0f } } }
    };
    return DataCreateRows(store, dmHashString64("Enemy"), dmHashString64("group1"), 2, enemies, out_ids);
}

Population creation · SoA input

Pass separate arrays for health, velocity and position directly to DataCreateRowsSoA. Each array contains one value per Enemy. Field hashes identify the arrays, so their order is independent of the registered layout. The library copies into the same stored byte rows without a temporary Enemy array.

C++ · public C API
static DataResult CreatePopulationSoA(HDataStore store, DataId out_ids[2])
{
    double      health[] = { 100.0, 80.0 };
    DataVector3 velocity[] = {
        { .m_Values = { 1.0f, 0.0f, 0.0f } },
        { .m_Values = { 1.0f, 0.0f, 0.0f } }
    };
    DataVector3 position[] = {
        { .m_Values = { 10.0f, 0.0f, 0.0f } },
        { .m_Values = { -20.0f, 0.0f, 5.0f } }
    };

    DataFieldArray fields[] = {
        { .m_Field = dmHashString64("health"), .m_Values = health },
        { .m_Field = dmHashString64("velocity"), .m_Values = velocity },
        { .m_Field = dmHashString64("position"), .m_Values = position }
    };
    return DataCreateRowsSoA(store, dmHashString64("Enemy"), dmHashString64("group1"), 2, 3, fields, out_ids);
}

DataRegisterTable copies the layout. DataCreateRows copies complete native rows and assigns the supplied group to each row. The registered layout determines the row size. DataCreateRowsSoA takes one array for every root field; inline structs use arrays of complete structs. Types and element sizes come from the registered layout. Both APIs copy the supplied values, so inputs can leave scope after the call. Both population functions return the insertion result; use the returned row IDs only after DATA_RESULT_OK. Each row’s initial values become its reset defaults. Store lifetime remains with the application.

Population creation - references

Create Enemy rows directly from C data, with a name string, dynamic attributes and a loot list. Both AoS and SoA creation copy these payloads into table-owned storage.

Query/Setup

The application already owns the store. Call CreateEnemyReferencesTable once before either creation function. This variant uses its own type name so it can coexist with the first example’s Enemy table. No query is needed.

Use DataReference for string, dynamic struct and list fields. It keeps each reference slot eight bytes on both 32-bit and 64-bit hosts. DataStructInput pairs a native struct with its member layout; DataListInput describes a contiguous array and its element kind. These are creation inputs, not the stored representation.

C++ · public C API
struct EnemyAttributes
{
    DataReference m_Faction;
    double        m_AlertRadius;
};

struct EnemyReferences
{
    DataReference m_Name;
    DataReference m_Attributes;
    DataReference m_Loot;
};

static const DataStructDesc* EnemyAttributesLayout()
{
    static const DataFieldDesc fields[] = {
        { .m_Field = dmHashString64("faction"), .m_Type = DATA_TYPE_STRING, .m_Offset = offsetof(EnemyAttributes, m_Faction) },
        { .m_Field = dmHashString64("alert_radius"), .m_Type = DATA_TYPE_NUMBER, .m_Offset = offsetof(EnemyAttributes, m_AlertRadius) }
    };
    static const DataStructDesc layout = { .m_Fields = fields, .m_FieldCount = 2, .m_Size = sizeof(EnemyAttributes) };
    return &layout;
}

static DataResult CreateEnemyReferencesTable(HDataStore store)
{
    DataFieldDesc fields[] = {
        { .m_Field = dmHashString64("name"), .m_Type = DATA_TYPE_STRING, .m_Offset = offsetof(EnemyReferences, m_Name) },
        { .m_Field = dmHashString64("attributes"), .m_Type = DATA_TYPE_STRUCT, .m_Offset = offsetof(EnemyReferences, m_Attributes) },
        { .m_Field = dmHashString64("loot"), .m_Type = DATA_TYPE_LIST, .m_Offset = offsetof(EnemyReferences, m_Loot) }
    };
    DataTableDesc table = {
        .m_Type = dmHashString64("EnemyReferences"),
        .m_Fields = fields,
        .m_FieldCount = 3,
        .m_RowStride = sizeof(EnemyReferences)
    };
    return DataRegisterTable(store, &table);
}

A dynamic struct has no m_Struct layout in the table’s field description: each supplied DataStructInput can describe different members. An inline struct instead sets DataFieldDesc.m_Struct and stores those members directly in every row.

Population creation · AoS

Supply complete Enemy rows. Here both rows use the same temporary attributes and mixed loot list ["coin", 25]. m_Types supplies the kind of each element; loot supplies its payload pointer. The library copies each row’s payloads; it does not retain these pointers or deduplicate equal strings on this creation path.

C++ · public C API
static DataResult CreatePopulationReferencesAoS(HDataStore store, DataGroupId group, DataId out_ids[2])
{
    EnemyAttributes attributes = { .m_Faction = { .m_String = "guards" }, .m_AlertRadius = 15.0 };
    DataStructInput object = { .m_Layout = EnemyAttributesLayout(), .m_Values = &attributes };
    double          amount = 25.0;
    DataValueType   loot_types[] = { DATA_TYPE_STRING, DATA_TYPE_NUMBER };
    const void*     loot[] = { "coin", &amount };
    DataListInput   list = { .m_Count = 2, .m_Values = loot, .m_Types = loot_types };

    EnemyReferences enemies[] = {
        { .m_Name = { .m_String = "Guard" }, .m_Attributes = { .m_Struct = &object }, .m_Loot = { .m_List = &list } },
        { .m_Name = { .m_String = "Captain" }, .m_Attributes = { .m_Struct = &object }, .m_Loot = { .m_List = &list } }
    };
    // Copies all payloads during this call; no pointers to these locals are retained.
    return DataCreateRows(store, dmHashString64("EnemyReferences"), group, 2, enemies, out_ids);
}

Population creation · SoA input

Supply separate arrays for names, attributes and loot. Every reference column has one DataReference per row, with the same mixed string/number loot list as the AoS version.

C++ · public C API
static DataResult CreatePopulationReferencesSoA(HDataStore store, DataGroupId group, DataId out_ids[2])
{
    EnemyAttributes attributes = { .m_Faction = { .m_String = "guards" }, .m_AlertRadius = 15.0 };
    DataStructInput object = { .m_Layout = EnemyAttributesLayout(), .m_Values = &attributes };
    double          amount = 25.0;
    DataValueType   loot_types[] = { DATA_TYPE_STRING, DATA_TYPE_NUMBER };
    const void*     loot[] = { "coin", &amount };
    DataListInput   list = { .m_Count = 2, .m_Values = loot, .m_Types = loot_types };

    DataReference   names[] = { { .m_String = "Guard" }, { .m_String = "Captain" } };
    DataReference   objects[] = { { .m_Struct = &object }, { .m_Struct = &object } };
    DataReference   lists[] = { { .m_List = &list }, { .m_List = &list } };
    DataFieldArray  fields[] = {
        { .m_Field = dmHashString64("name"), .m_Values = names },
        { .m_Field = dmHashString64("attributes"), .m_Values = objects },
        { .m_Field = dmHashString64("loot"), .m_Values = lists }
    };
    // Copies all payloads during this call; no pointers to these locals are retained.
    return DataCreateRowsSoA(store, dmHashString64("EnemyReferences"), group, 2, 3, fields, out_ids);
}

All input arrays, strings and descriptors only need to live through the call. The supplied group is assigned to both rows. Use out_ids after DATA_RESULT_OK; on error no rows are added. Both APIs reserve string/list payload storage for the batch. Dynamic attributes use separate child rows with shared member metadata; lists keep packed containers. Fixed-size fields keep the native copy path.

Homogeneous lists keep one m_Type and a contiguous native array, such as double[] or DataReference[]. Set m_Types to supply different kinds in the same list.

List input and memory ownership

The examples above put two different kinds in one list: the string "coin" and the number 25.0. loot holds pointers to those input values; loot_types identifies their kinds.

Building DataListInput only borrows those pointers. During DataCreateRows or DataCreateRowsSoA, the library synchronously copies every value, string and nested container into table-owned storage. Dynamic attributes share copied member metadata in a child table; list elements retain their kinds in the packed list. The stored row refers to that owned payload; no pointer to amount, loot, loot_types, list or the local struct inputs is retained.

After the call returns, all those stack variables may leave scope. Changing or freeing the inputs cannot change the created rows. Their copied initial values remain available for reset.

The caller owns the inputs; each Enemy exclusively owns its copied attributes row. Removing an Enemy releases its child rows for reuse. Reset releases replacement child rows and restores the original attributes. String/list arena allocations remain until the table is unregistered or the store is destroyed.

Replace and reset a string

After query iteration and reservations finish, use a returned row ID to replace its name. The setter copies this temporary string. DataResetRow(store, out_ids[0]) restores all that row’s original values, including its name, attributes and loot.

C++ · public C API
static DataResult RenameReferenceEnemy(HDataStore store, DataId enemy)
{
    char name[] = "Guard captain";
    return DataSetFieldString(store, enemy, dmHashString64("name"), name);
}

DataFieldGetString returns a borrowed string. Finish using it before a store write, reset or iterator step. Remove rows with DataRemoveRow; their default and replacement payload allocations remain table-owned until DataUnregisterTable or store destruction.

Strings have public read/write access. Dynamic structs and lists can now be constructed through these public creation APIs; public traversal and replacement of their contents remain future work.

02 / 08

Spawn wave

Add new Enemies to an existing store in batches of up to 100.

Query/Setup

No query is needed. Register the Enemy table once, as shown in Create population. Supply one group for the wave and the initial positions, plus space for the returned row IDs. Each Enemy starts with 100 health and velocity (1, 0, 0).

Wave insertion

C++ · public C API
static DataResult SpawnWave(HDataStore store, DataGroupId group, uint32_t count, const DataVector3* positions, DataId* out_ids, uint32_t* out_added)
{
    Enemy defaults = { .m_Health = 100.0, .m_Velocity = { .m_Values = { 1.0f, 0.0f, 0.0f } } };

    *out_added = 0;
    while (*out_added < count)
    {
        uint32_t first = *out_added;
        uint32_t batch_count = count - first;
        if (batch_count > 100)
            batch_count = 100;

        Enemy enemies[100];
        for (uint32_t i = 0; i < batch_count; ++i)
        {
            enemies[i] = defaults;
            enemies[i].m_Position = positions[first + i];
        }

        DataResult result = DataCreateRows(store, dmHashString64("Enemy"), group, batch_count, enemies, out_ids + first);
        if (result != DATA_RESULT_OK)
            return result;
        *out_added += batch_count;
    }
    return DATA_RESULT_OK;
}

DataCreateRows creates the rows, copies the supplied Enemy values, and returns stable DataId handles. Inputs can be released after the call. On error, out_added identifies the successfully added prefix of out_ids; those rows remain in the store. Add rows while the store is unlocked and no query reservation is active.

The benchmark keeps two Boids flock queries, Explosion and nearby-light queries alive to include the cost of maintaining existing queries during insertion. They are not required for spawning.

03 / 08

Despawn wave

Remove selected instances by their stable row IDs.

Query/Setup

No query is needed. The caller owns ids_by_type (IDs returned when adding rows) and order (which rows to remove). DataRemoveRow uses those IDs directly; it does not run a query.

Wave removal

C++ · public C API
static DataResult DespawnWave(HDataStore store, DataId* const ids_by_type[6], const struct RowKey* order, uint32_t initial_count, uint32_t* out_removed)
{
    *out_removed = 0;
    for (uint32_t i = 0; i < initial_count / 100; ++i)
    {
        struct RowKey key = order[i];
        DataId        id = ids_by_type[key.m_Type][key.m_Row];
        DataResult    result = DataRemoveRow(store, id);
        if (result != DATA_RESULT_OK)
            return result;
        ++*out_removed;
    }
    return DATA_RESULT_OK;
}

Row removal swaps dense storage while preserving other live IDs. Removed IDs become stale. On error, out_removed reports the successfully removed prefix; the caller can resume at the failing entry. To remove during a query, collect IDs first and apply deletions after unlocking or after all query reservations end.

Boids

Steer a flock using nearby agents, targets and an obstacle. Read a completed snapshot so an agent never sees another agent's partially updated position.

Query/Setup

Create one query per flock: pass dmHashString64("player") or dmHashString64("enemy") for this fixture. Both position and velocity are writable. Each flock owns a snapshot large enough for its query's population and a reusable spatial index; reserve that storage before updating.

C++ · public C API
static HDataQuery CreateBoidsQuery(HDataStore store, uint64_t flock_tag, uint32_t* out_position, uint32_t* out_velocity)
{
    DataQueryField fields[] = {
        { .m_Field = dmHashString64("position"), .m_Type = DATA_TYPE_VECTOR3, .m_Access = DATA_ACCESS_READ_WRITE },
        { .m_Field = dmHashString64("velocity"), .m_Type = DATA_TYPE_VECTOR3, .m_Access = DATA_ACCESS_READ_WRITE }
    };
    DataQueryDesc desc = { .m_AllTags = &flock_tag, .m_AllTagCount = 1, .m_Fields = fields, .m_FieldCount = 2 };
    HDataQuery    query = NULL;
    if (DataCreateQuery(store, &desc, &query) == DATA_RESULT_OK)
    {
        *out_position = DataQueryFindField(query, &fields[0]);
        *out_velocity = DataQueryFindField(query, &fields[1]);
    }
    return query;
}

Query iteration

The first pass copies position and velocity into the snapshot. The game helper groups agents into 8-unit cells, compares full cell coordinates to distinguish hash collisions, and accumulates positions and velocities within this flock. The second pass applies alignment, separation, target attraction and radius-30 obstacle avoidance, then writes speed-25 velocity and position. The lock keeps query order stable across both passes. Reuse each flock's buffers on later frames.

C++ · public C API
struct Boid
{
    DataVector3 m_Position;
    DataVector3 m_Velocity;
};

// Game-owned spatial index and steering helpers, not datastore API functions.
// Build cells from the completed snapshot, retaining full cell coordinates.
// Steer using cell-local alignment/separation, target attraction and avoidance.
struct BoidsGrid;
void        BuildBoidCells(BoidsGrid* grid, const Boid* snapshot, uint32_t num_rows);
Boid        SteerBoid(const BoidsGrid* grid, const Boid* snapshot, uint32_t row, float dt);

static void Boids(HDataStore store, HDataQuery query, uint32_t position_field, uint32_t velocity_field, Boid* snapshot, BoidsGrid* grid)
{
    DataStoreLock(store);
    uint32_t     index = 0;
    DataIterator it = DataQueryIter(query);
    while (DataIterNext(&it) == DATA_RESULT_OK)
    {
        DataRowIterator rows = DataIterRows(&it);
        while (DataRowIterNext(&rows) == DATA_RESULT_OK)
        {
            snapshot[index++] = Boid {
                .m_Position = *DataRowIterGetVector3(&rows, position_field),
                .m_Velocity = *DataRowIterGetVector3(&rows, velocity_field)
            };
        }
    }

    BuildBoidCells(grid, snapshot, index);
    index = 0;
    it = DataQueryIter(query);
    while (DataIterNext(&it) == DATA_RESULT_OK)
    {
        DataRowIterator rows = DataIterRows(&it);
        while (DataRowIterNext(&rows) == DATA_RESULT_OK)
        {
            Boid next = SteerBoid(grid, snapshot, index++, 1.0f / 64.0f);
            *DataRowIterGetVector3Mut(&rows, position_field) = next.m_Position;
            *DataRowIterGetVector3Mut(&rows, velocity_field) = next.m_Velocity;
        }
    }
    DataStoreUnlock(store);
}

The spatial-index and steering helpers are application code. They operate on the snapshot; only the public data API reads or writes stored rows. The benchmark includes both passes, cell construction and steering, with no rendering or game-object work.

Explosion

Push Players, Enemies and Breakables away from an explosion, apply damage from the impulse, and mark depleted instances for later removal.

Query/Setup

Match position and health on the same row, regardless of type or field offset. Declare both writable: the game helpers update position and health.

C++ · public C API
static HDataQuery CreateExplosionQuery(HDataStore store, uint32_t* out_position, uint32_t* out_health)
{
    DataQueryField fields[] = {
        { .m_Field = dmHashString64("position"), .m_Type = DATA_TYPE_VECTOR3, .m_Access = DATA_ACCESS_READ_WRITE },
        { .m_Field = dmHashString64("health"), .m_Type = DATA_TYPE_NUMBER, .m_Access = DATA_ACCESS_READ_WRITE }
    };
    DataQueryDesc desc = { .m_Fields = fields, .m_FieldCount = 2 };
    HDataQuery    query = NULL;
    if (DataCreateQuery(store, &desc, &query) == DATA_RESULT_OK)
    {
        *out_position = DataQueryFindField(query, &fields[0]);
        *out_health = DataQueryFindField(query, &fields[1]);
    }
    return query;
}

Query iteration

The caller supplies the two game helpers: MoveExplosion updates position and returns an impulse (zero outside its area of effect); ApplyDamage updates health and returns a negative value when the instance should be removed. The removal branch is an integration point: collect IDs there, then remove them after unlocking or after all query reservations end.

C++ · public C API
// Game-specific helpers implemented by the caller, not datastore API functions.
float       MoveExplosion(const DataVector3* explosion_center, DataVector3* position);
double      ApplyDamage(double* health, float impulse);

static void ExplosionRows(DataIterator* it, uint32_t position_field, uint32_t health_field, const DataVector3* explosion_center)
{
    while (DataIterNext(it) == DATA_RESULT_OK)
    {
        DataRowIterator rows = DataIterRows(it);
        while (DataRowIterNext(&rows) == DATA_RESULT_OK)
        {
            DataVector3* position = DataRowIterGetVector3Mut(&rows, position_field);
            double*      health = DataRowIterGetNumberMut(&rows, health_field);
            float        impulse = MoveExplosion(explosion_center, position); // Apply force.
            if (ApplyDamage(health, impulse) < 0)
            {
                // Mark for removal: save DataRowIterGetId(&rows) in a caller-owned list.
                // Remove after iteration; each worker uses its own list.
            }
        }
    }
}

static void Explosion(HDataStore store, HDataQuery query, uint32_t position_field, uint32_t health_field, const DataVector3* explosion_center)
{
    DataStoreLock(store);
    DataIterator it = DataQueryIter(query);
    ExplosionRows(&it, position_field, health_field, explosion_center);
    DataStoreUnlock(store);
}

The game helpers illustrate application logic. The timed benchmark applies fixed damage within radius 50; this example also shows writable position access and deferred removal.

Nearby light contribution

Select tables tagged light (SpotLight and PointLight) and sum their contribution inside radius 50: (r + g + b) × intensity × (1 − distance² / 2500).

Query/Setup

Register both light tables with the dmHashString64("light") tag. The query requires that tag through m_AllTags, plus all three fields below; having the fields alone does not match. Tags belong to the table and apply to all its rows. position belongs to the outer light row. Both SpotLight and PointLight contain Light light; light.color and light.intensity are full-name hashes of its inline members. Their bindings resolve once per matching table.

C++ · public C API
static HDataQuery CreateNearbyLightsQuery(HDataStore store, uint32_t* out_position, uint32_t* out_color, uint32_t* out_intensity)
{
    DataQueryField fields[] = {
        { .m_Field = dmHashString64("position"), .m_Type = DATA_TYPE_VECTOR3 },
        { .m_Field = dmHashString64("light.color"), .m_Type = DATA_TYPE_VECTOR3 },
        { .m_Field = dmHashString64("light.intensity"), .m_Type = DATA_TYPE_NUMBER }
    };
    uint64_t      light_tag = dmHashString64("light");
    DataQueryDesc desc = { .m_AllTags = &light_tag, .m_AllTagCount = 1, .m_Fields = fields, .m_FieldCount = 3 };
    HDataQuery    query = NULL;
    if (DataCreateQuery(store, &desc, &query) == DATA_RESULT_OK)
    {
        *out_position = DataQueryFindField(query, &fields[0]);
        *out_color = DataQueryFindField(query, &fields[1]);
        *out_intensity = DataQueryFindField(query, &fields[2]);
    }
    return query;
}

Query iteration

C++ · public C API
static double NearbyLightsRows(DataIterator* it, uint32_t position_field, uint32_t color_field, uint32_t intensity_field)
{
    double contribution = 0;
    while (DataIterNext(it) == DATA_RESULT_OK)
    {
        DataRowIterator rows = DataIterRows(it);
        while (DataRowIterNext(&rows) == DATA_RESULT_OK)
        {
            const DataVector3* position = DataRowIterGetVector3(&rows, position_field);
            float              distance_squared = DistanceSquared(position);
            if (distance_squared <= 2500.0f)
            {
                const DataVector3* color = DataRowIterGetVector3(&rows, color_field);
                double             intensity = *DataRowIterGetNumber(&rows, intensity_field);
                double             rgb = (double)color->m_Values[0] + color->m_Values[1] + color->m_Values[2];
                contribution += rgb * intensity * (1.0 - distance_squared / 2500.0);
            }
        }
    }
    return contribution;
}

static double NearbyLights(HDataStore store, HDataQuery query, uint32_t position_field, uint32_t color_field, uint32_t intensity_field)
{
    DataStoreLock(store);
    DataIterator it = DataQueryIter(query);
    double       contribution = NearbyLightsRows(&it, position_field, color_field, intensity_field);
    DataStoreUnlock(store);
    return contribution;
}

This is a simple lighting workload, not a renderer: spot cone angles and individual light ranges do not enter the formula.

07 / 08

Shuffled position lookup

Read every initial instance’s position once in seeded shuffled order, then sum the coordinates.

Query/Setup

No query is created. Prepare a shuffled array of RowKey { type, row } entries and retain the runtime IDs from creation. The RowKey definition is in the shared helpers at the end.

ID access

C++ · public C API
static DataResult ShuffledPositionLookup(HDataStore store, DataId* const ids_by_type[6], const struct RowKey* order, uint32_t count, double* out_sum)
{
    uint64_t position_field = dmHashString64("position");
    double   sum = 0;
    for (uint32_t first = 0; first < count; first += 256)
    {
        uint32_t batch_count = count - first;
        if (batch_count > 256)
            batch_count = 256;
        DataId      ids[256];
        DataVector3 positions[256];
        for (uint32_t i = 0; i < batch_count; ++i)
        {
            struct RowKey key = order[first + i];
            ids[i] = ids_by_type[key.m_Type][key.m_Row];
        }
        DataResult result = DataFieldGetVector3Batch(store, batch_count, ids, position_field, positions);
        if (result != DATA_RESULT_OK)
            return result;
        for (uint32_t i = 0; i < batch_count; ++i)
        {
            const float* p = positions[i].m_Values;
            sum += (double)p[0] + p[1] + p[2];
        }
    }
    *out_sum = sum;
    return DATA_RESULT_OK;
}

Gather IDs in groups of 256 and read them with the typed batch getter. It returns one aggregate status; consume outputs only on success. The helper leaves out_sum untouched on failure. Run outside concurrent query reservations.

Threaded update

Run Movement, Explosion, Regenerate and nearby-light updates on workers while the main thread prepares content. Then replace content and spawn/despawn enemy waves.

Locking scope

DataStoreLock holds the whole store mutex throughout single-threaded traversal. The job path uses DataQueryTryBegin: under that mutex it checks conflicts, prepares row ranges and records an active reservation, then releases the mutex. The reservation remains active while workers iterate. Structural operations acquire the same mutex and return DATA_RESULT_LOCKED if any reservation is active, so they cannot add, remove, move or free row storage during iteration. The caller finishes every job before calling DataQueryEnd; structural changes can succeed after the last reservation ends. Rejected operations are not queued automatically.

Reservations also protect requested field bytes on matching tables: compatible queries can access different tables or non-overlapping fields concurrently. There are no per-table mutexes.

Concurrency follow-up: any active query currently blocks additions/removals across the entire store, including unrelated tables. Investigate allowing structural changes on unreserved tables while preserving active row pointers, IDs and query bindings. Also examine contention during query admission and range rebuilding. These are planned investigations; the examples use the current synchronization rules.

This concurrency workload uses simple movement alongside Explosion, Regenerate and nearby lights. It keeps the movement kernel small to exercise query reservations and content streaming independently of the standalone Boids simulation.

C++ · public C API
static HDataQuery CreateMovementQuery(HDataStore store, uint32_t* out_position, uint32_t* out_velocity)
{
    DataQueryField fields[] = {
        { .m_Field = dmHashString64("position"), .m_Type = DATA_TYPE_VECTOR3, .m_Access = DATA_ACCESS_READ_WRITE },
        { .m_Field = dmHashString64("velocity"), .m_Type = DATA_TYPE_VECTOR3 }
    };
    DataQueryDesc desc = { .m_Fields = fields, .m_FieldCount = 2 };
    HDataQuery    query = NULL;
    if (DataCreateQuery(store, &desc, &query) == DATA_RESULT_OK)
    {
        *out_position = DataQueryFindField(query, &fields[0]);
        *out_velocity = DataQueryFindField(query, &fields[1]);
    }
    return query;
}

static void MovementRows(DataIterator* it, uint32_t position_field, uint32_t velocity_field)
{
    while (DataIterNext(it) == DATA_RESULT_OK)
    {
        DataRowIterator rows = DataIterRows(it);
        while (DataRowIterNext(&rows) == DATA_RESULT_OK)
        {
            DataVector3*       position = DataRowIterGetVector3Mut(&rows, position_field);
            const DataVector3* velocity = DataRowIterGetVector3(&rows, velocity_field);
            for (uint32_t axis = 0; axis < 3; ++axis)
                position->m_Values[axis] += velocity->m_Values[axis] * 0.015625f;
        }
    }
}

// QueryJobs and the worker callbacks are defined in the jobs example below.
static bool CreateUpdates(HDataStore store, struct QueryJobs updates[4], struct QueryRange* ranges[4], uint32_t range_capacity)
{
    FJobProcess processes[] = { MovementJob, ExplosionJob, RegenerateJob, NearbyLightsJob };
    for (uint32_t i = 0; i < 4; ++i)
    {
        struct QueryJobs group = {
            .m_Query = NULL,
            .m_Process = processes[i],
            .m_Ranges = ranges[i],
            .m_RangeCapacity = range_capacity,
            .m_State = UPDATE_WAITING
        };
        updates[i] = group;
    }
    updates[0].m_Query = CreateMovementQuery(store, &updates[0].m_Position, &updates[0].m_Velocity);
    updates[1].m_Query = CreateExplosionQuery(store, &updates[1].m_Position, &updates[1].m_Health);
    updates[2].m_Query = CreateRegenerateQuery(store, &updates[2].m_Health);
    updates[3].m_Query = CreateNearbyLightsQuery(store, &updates[3].m_Position, &updates[3].m_Color, &updates[3].m_Intensity);
    for (uint32_t i = 0; i < 4; ++i)
    {
        if (updates[i].m_Query == NULL)
        {
            for (uint32_t j = 0; j < 4; ++j)
            {
                if (updates[j].m_Query)
                    DataDestroyQuery(updates[j].m_Query);
                updates[j].m_Query = NULL;
            }
            return false;
        }
    }
    return true;
}

Main-thread scheduling

Try waiting updates in a seeded, shuffled order each frame. A BUSY query stays pending; other compatible queries can still start. The helpers and job state used here are defined in the final example.

C++ · public C API
// The caller supplies content preparation, structural commits and idle policy.
// order is a seeded permutation of { Movement, Explosion, Regenerate, Lights }.
static bool ThreadedFrame(HJobContext jobs, struct QueryJobs updates[4], const uint32_t order[4], void* content, void (*prepare)(void*), void (*commit)(void*), void (*idle)(void))
{
    for (uint32_t i = 0; i < 4; ++i)
    {
        updates[i].m_State = UPDATE_WAITING;
        updates[i].m_Failed = false;
    }
    bool     success = false;
    uint32_t prepared = 0, done = 0;
    while (done != 4)
    {
        uint32_t progress = 0;
        for (uint32_t i = 0; i < 4; ++i)
        {
            struct QueryJobs* group = &updates[order[i]];
            if (group->m_State != UPDATE_WAITING)
                continue;
            DataResult result = DataQueryTryBegin(group->m_Query);
            if (result == DATA_RESULT_BUSY)
                continue; // Retry after other updates release their reservations.
            if (result != DATA_RESULT_OK)
                goto complete;
            SubmitQueryRanges(jobs, group);
            if (group->m_Failed)
                goto complete;
            progress = 1;
        }
        if (!prepared)
        {
            prepare(content); // Resource preparation only; no datastore mutation.
            prepared = 1;
        }
        uint32_t before = 0, after = 0;
        for (uint32_t i = 0; i < 4; ++i)
            before += updates[i].m_Remaining;
        JobSystemUpdate(jobs, 0); // Main-thread callbacks release finished queries.
        done = 0;
        for (uint32_t i = 0; i < 4; ++i)
        {
            after += updates[i].m_Remaining;
            done += updates[i].m_State == UPDATE_DONE;
            if (updates[i].m_Failed)
                goto complete;
        }
        if (done != 4 && !progress && before == after)
            idle(); // Yield while workers run.
    }
    success = true;

complete:
    for (uint32_t i = 0; i < 4; ++i)
        if (updates[i].m_State == UPDATE_RUNNING && !WaitForQueryJobs(jobs, &updates[i], idle))
            success = false;
    if (success)
        commit(content); // Replace mixed content; spawn/despawn enemy waves.
    return success;
}
Main thread: reserve queries, push jobs, process completion callbacks and retry conflicts. Prepare incoming blob handles from bytes already in memory while workers run. After every update finishes, unload/reload mixed bundles and apply variable enemy waves.
Workers: update existing rows in their assigned ranges; each job has its own iterator and reduction result. They do not add or remove rows.

The prepare and commit callbacks are caller-supplied integration points. Use DataLoadBlob during preparation, then DataRemoveBlob/DataAddBlob and temporary handle cleanup during commit. Keep borrowed blob bytes alive until every resource and instance reference is gone. On failure, ThreadedFrame drains running jobs and returns false without calling commit. The caller releases any prepared content; completed row writes are not rolled back.

Caller-owned parallelism

Split one query across multiple jobs

Reserve once, divide the matching rows into disjoint 4,096-row ranges, and give each job its own iterator. The datastore owns synchronization; the caller owns the job system.

TryBegin→GetRowCount→Push range jobs→Complete all jobs→QueryEnd

first and count address the reserved sequence of matching rows, which may span multiple tables. They are not row IDs or per-table offsets. Disjoint ranges permit concurrent writes within one reservation; the caller is responsible for making them disjoint.

1. Keep group and range storage stable

Allocate reusable range arrays before dispatch. Each group needs capacity for ceil(maximum_matching_rows / 4096) ranges, including later enemy waves. State and completion counters are main-thread-only; workers touch only their own rows and range result.

3. End the reservation after the final completion callback

JobSystemUpdate delivers callbacks on the main thread after worker completion. Record job failures, wait for every callback, then release query access once. Use the reduction only when WaitForQueryJobs returns true.

C++ · public C API
static void FinishQueryJobs(struct QueryJobs* group)
{
    group->m_Sum = 0;
    if (!group->m_Failed)
        for (uint32_t i = 0; i < group->m_RangeCount; ++i)
            group->m_Sum += group->m_Ranges[i].m_Sum;
    DataQueryEnd(group->m_Query);
    group->m_State = UPDATE_DONE;
}

// Invoked on the main thread by JobSystemUpdate, after the worker has finished.
static void RangeFinished(HJobContext jobs, HJob job, enum JobSystemStatus status, void* context, void* data, int32_t result)
{
    (void)jobs;
    (void)job;
    (void)data;
    struct QueryJobs* group = (struct QueryJobs*)context;
    if (status != JOBSYSTEM_STATUS_FINISHED || result != 0)
        group->m_Failed = true;
    if (--group->m_Remaining == 0)
        FinishQueryJobs(group);
}

static bool WaitForQueryJobs(HJobContext jobs, struct QueryJobs* group, void (*idle)(void))
{
    while (group->m_State != UPDATE_DONE)
    {
        JobSystemUpdate(jobs, 0);
        if (group->m_State != UPDATE_DONE)
            idle();
    }
    return !group->m_Failed; // All callbacks finished and DataQueryEnd has run.
}

4. Push each row range to the job system

Get the row count only after a successful reservation. All jobs share that reservation, but each receives a distinct range and its own result storage. If the range buffer is too small or job creation fails, record the failure and drain any jobs already submitted. Keep the job context alive and new job handles private to the submitting thread.

C++ · public C API
// Call only after DataQueryTryBegin succeeds for this group.
static void SubmitQueryRanges(HJobContext jobs, struct QueryJobs* group)
{
    const uint32_t chunk = 4096;
    uint32_t       count = DataQueryGetRowCount(group->m_Query);
    uint32_t       job_count = count / chunk + (count % chunk != 0);
    group->m_RangeCount = group->m_Remaining = 0;
    group->m_State = UPDATE_RUNNING;
    group->m_Failed = false;
    if (job_count > group->m_RangeCapacity)
    {
        group->m_Failed = true;
        FinishQueryJobs(group);
        return;
    }
    for (uint32_t i = 0; i < job_count; ++i)
    {
        uint32_t          first = i * chunk;
        uint32_t          remaining = count - first;
        struct QueryRange range = {
            .m_Group = group,
            .m_First = first,
            .m_Count = remaining < chunk ? remaining : chunk
        };
        group->m_Ranges[i] = range;
        struct Job job = {
            .m_Process = group->m_Process,
            .m_Callback = RangeFinished,
            .m_Context = group,
            .m_Data = &group->m_Ranges[i]
        };
        HJob handle = JobSystemCreateJob(jobs, &job);
        if (handle == 0)
        {
            group->m_Failed = true;
            break; // Already submitted jobs must finish before releasing the query.
        }
        // This thread owns the new handle; the job context stays alive through completion.
        JobSystemPushJob(jobs, handle);
        ++group->m_RangeCount;
        ++group->m_Remaining;
    }
    if (group->m_Remaining == 0)
        FinishQueryJobs(group); // Empty queries and failed submissions still release access.
}

5. Start and wait from the caller

Create an HJobContext with JobSystemCreate before dispatch. Initialize a group with a Movement query, MovementJob and its preallocated range array (as in CreateUpdates). After TryMovementJobs returns OK, always call WaitForQueryJobs and check its boolean result. On BUSY, do other work and retry. The wait helper is defined with the completion callback above.

C++ · public C API
// jobs and group are initialized once; group uses MovementJob and a Movement query.
// Its range buffer covers ceil(maximum_matching_rows / 4096) jobs.
static DataResult TryMovementJobs(HJobContext jobs, struct QueryJobs* group)
{
    DataResult result = DataQueryTryBegin(group->m_Query);
    if (result != DATA_RESULT_OK)
        return result; // BUSY means no reservation was acquired and no jobs were queued.
    SubmitQueryRanges(jobs, group);
    return DATA_RESULT_OK;
}

// After TryMovementJobs returns OK, always call WaitForQueryJobs(jobs, group, idle).
// It returns false if submission or a worker failed, after draining all callbacks.
// On BUSY, no reservation was acquired; do other work and retry instead.

The full threaded frame uses the same submission/completion path for all four updates, allowing independent queries to overlap. Read/read access can overlap on the same table; an overlapping writer conflicts. Group filters do not narrow reservations. Structural mutation waits until every active reservation has ended. Failed groups still retain their reservation until all submitted jobs finish; the caller receives failure after cleanup.

Cleanup

Finish every iterator and job before destroying queries. Destroy any queries you created when they are no longer needed. For threaded updates:

C++ · public C API
// After the last iteration/job callback; the caller owns these handles.
static DataResult DestroyUpdates(struct QueryJobs updates[4])
{
    for (uint32_t i = 0; i < 4; ++i)
    {
        if (updates[i].m_Query == NULL)
            continue;
        DataResult result = DataDestroyQuery(updates[i].m_Query);
        if (result != DATA_RESULT_OK)
            return result; // Keep the remaining handles so the caller can finish work and retry.
        updates[i].m_Query = NULL;
    }
    return DATA_RESULT_OK;
}
