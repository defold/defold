Result

The production Vulkan path now reuses fence-retired, persistently mapped
backing allocations for STREAM_DRAW and DYNAMIC_DRAW vertex/index buffers.
The memory type is unchanged: HOST_VISIBLE | HOST_COHERENT, with the existing
first-match selection. No VRAM placement or staging policy is introduced.

At 50,000 small quads, CPU upload and complete benchmark-loop medians are:

  Layout     Upload before -> after     Complete loop before -> after
  Expanded      626 -> 273 us                 1.580 -> 0.925 ms
  Compact       322 -> 168 us                 0.817 -> 0.543 ms

That is about 56% / 48% less CPU upload time and 41% / 34% less complete-loop
time respectively. Compact complete-loop medians at 50,000 sprites also improve
for overdraw (0.886 -> 0.787 ms), 64 batches (0.843 -> 0.533 ms), and three
repeated passes (2.012 -> 1.355 ms). These are graphics-harness measurements,
not full-game FPS or full sprite-component timings.

GPU pass time does not consistently improve. For example, compact small-quads
GPU time is 273 -> 334 us despite the faster complete loop. The CPU submits
work sooner; frame overlap, shared-target dependencies and memory access still
affect the TOP_OF_PIPE/BOTTOM_OF_PIPE interval. This change removes CPU-side
allocation/map/unmap churn; it does not solve system-memory GPU fetch costs.

Implementation and limits

- Each logical dynamic vertex/index buffer retains its active allocation and
  at most three spare backings. Eligible completed backings are selected by
  capacity; allocations remain mapped while cached.
- A monotonic frame serial identifies uses. Completion advances only after
  waiting the actual submission fence. A matching frame-slot index alone is
  insufficient: earlier draws in the current frame can still reference it.
- Replacements after a draw select another backing. Multiple replacements in
  one frame can overflow the cache; evictions use existing deferred destruction.
- Full updates track logical size separately from allocation capacity, allowing
  shrink/reuse without reporting the wrong buffer size. Existing zero-size
  update behavior is preserved.
- Partial updates use a different backing when necessary and preserve untouched
  bytes, including nonzero offsets. That preservation copies the logical buffer
  on the CPU; this path is intended for CPU-authored vertex/index data.
- Deletion and switching to static replacement retire both active and cached
  storage. Static, storage and transfer-capable buffers retain their old paths.
- Spare count is bounded, not a global byte budget. Large capacities can remain
  cached after a workload shrinks until eviction or deletion. This trades some
  retained host-visible memory for fewer allocations; production memory profiles
  on other workloads and devices remain useful before merging.
- No public API, sprite material or shader contract changes. Only the Windows
  Vulkan runtime was tested; other Vulkan platforms have not been run here.

Benchmark method

compare_vulkan_buffer_reuse.py interleaves fresh processes from the saved
pre-change executable and rebuilt production executable. Both use native
Vulkan uploads, not the benchmark-only memory-policy implementations.
Two counts (10,000/50,000), two layouts (expanded/compact), four scenarios
(small/overdraw/64 batches/three repeated passes), three processes per case.
Each process has 600 warmup frames, then five samples of 120 measured frames.
96 processes / 480 samples completed: 57,600 measured and 57,600 warmup frames.

Input transforms/UVs are fixed, but packing, upload and drawing occur every
frame. The complete loop includes synchronization, presentation and the final
GPU-query drain. The hidden 1024x768 target/window and swap interval zero match
the previous memory experiment. GPU/CPU clocks and desktop load are uncontrolled.
Only the pass GPU timer is enabled; no additional pre-upload query is used.
Values are medians of process medians of sample means; ranges are the minimum
and maximum process medians, not confidence intervals. CPU and GPU overlap;
do not add their times or compare to the earlier moving-fixture loop directly.

Reproduction (Defold build environment, repository root)

Before applying the production change, build benchmark_sprite_quads_gpu and
save its executable. Then build the changed sources:

  cmake --build engine/build/x86_64-win32 --target test_vulkan_buffer_reuse test_graphics benchmark_sprite_quads_gpu
  engine/graphics/build/x86_64-win32/src/test/test_vulkan_buffer_reuse.exe
  engine/graphics/build/x86_64-win32/src/test/test_graphics.exe
  python engine/graphics/src/test/compare_vulkan_buffer_reuse.py tmp/vulkan-buffer-reuse/before.exe engine/graphics/build/x86_64-win32/src/test/benchmark_sprite_quads_gpu.exe tmp/vulkan-buffer-reuse/results

Configure performance_tests and WITH_VULKAN=ON to build the benchmark, as in
sprite_gpu_memory_benchmark_results.txt. Python needs Pillow. The new GPU test
is a manual desktop target, requires Vulkan and the Khronos validation layer,
and does not run in the default test set. For synchronization validation set:
  VK_LAYER_ENABLES=VK_VALIDATION_FEATURE_ENABLE_SYNCHRONIZATION_VALIDATION_EXT,VALIDATION_CHECK_ENABLE_SYNCHRONIZATION_VALIDATION_QUEUE_SUBMIT
