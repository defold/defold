Implemented production policy and paired measurements
-----------------------------------------------------
Branch: codex/vulkan-staged-vertex-index-uploads
All vertex/index usage hints now use device-local destinations and reusable,
persistently mapped host staging. Destinations retain capacity across updates;
growth replaces the allocation and retires its predecessor after GPU completion.
Partial writes copy only the changed range. Transfer barriers order copies against
previous draws and uploads, preserving earlier draws without CPU reads of old data.
The upload pools are shared with storage buffers and reused only after their frame
fence completes. Pre-frame calls snapshot caller bytes into a separate pool; the
next successful BeginFrame transfers ownership to its fenced pool and records the
queued copies. This batches pre-frame work without per-upload submissions/waits.
Deleting or growing a buffer cancels its obsolete queued copies.

GetMemoryTypeIndex now separates requirements from preferred/avoided properties.
Device-local destinations prefer non-host-visible memory; host-coherent staging
prefers non-device-local memory. These are soft preferences, allowing UMA layouts.
The old mapped vertex/index copy-on-write allocation cache is removed. This does
not add memory suballocation for destinations, budget management, VMA, or GPU-only
mesh-component storage. Those remain separate work.

original executable and the fixed executable were interleaved in randomized pairs:

Historical candidate comparison
------------------------------

Modes
-----
host:   Persistently mapped HOST_VISIBLE | HOST_COHERENT system memory.
bar:    Persistently mapped DEVICE_LOCAL | HOST_VISIBLE | HOST_COHERENT memory.
staged: Persistently mapped host staging memory, vkCmdCopyBuffer into DEVICE_LOCAL
        vertex/index buffers, and transfer-to-vertex/index barriers.

The actual selected memory types on this machine were:
  host: type 3, flags 0x6, heap 1 (system memory)
  bar: type 5, flags 0x7, heap 2 (214 MiB host-visible device-local heap)
  staged destination: type 1, flags 0x1, heap 0 (about 7.84 GiB device-local heap)
Staged upload sources prefer a non-device-local host-visible heap. The benchmark
fails or explicitly skips unavailable modes instead of silently relabeling them.

Method
------
- 32-byte vertices: two vec4 attributes, all components consumed by the shader.
- Sequential 32-bit indices; index bytes are one eighth of vertex bytes.
- Byte sizes are rounded down to a whole number of triangles.
- Most triangles are clipped to isolate vertex/index fetch rather than fill rate.
  A visible triangle and alternating vertex/index uploads provide pixel checks.
- Each mode preallocates the same 3 destination buffer pairs, one per frame
  slot. Staged mode also owns one upload buffer per slot. No steady-state buffer
  allocation, mapping, per-upload submission, or per-upload fence wait occurs.
  BeginFrame waits for the slot fence before the CPU overwrites its contents.
- Resident: upload each slot once during warm-up, then repeatedly draw it.
- Stream: upload the complete vertex and index contents every frame, draw once.
- Stream4: upload once per frame, draw the same geometry four times.
- Occasional: each slot receives fresh data on its first use in each 60-frame epoch.
  This means up to 3 uploads per epoch, not one upload globally.
- CPU upload time includes memcpy and, for staging, copy/barrier recording. It
  excludes data generation, initial allocations, and frame-fence/presentation work.
- GPU time uses timestamp queries from before copies to after draws. It includes
  render-target clear/setup and any staged copy, but excludes CPU memcpy and present.
  Query results are read only after the frame fence (or final device idle) completes.
- Wall time includes BeginFrame, upload, draw recording, submission, presentation,
  and the final drain. CPU and GPU work overlap, so their times must not be added.
- Hidden 64x64 window and offscreen render target. Small workloads are dominated
  by CPU/window-system overhead in the wall metric; do not rank them by wall time.
- Main matrix: 5 trials, 120 warm-up + 480 measured frames per process; 36 cases.
  Workloads and mode order are shuffled with seed 13751. Cases run sequentially.
- Longer confirmation: 3 trials, 600 warm-up + 1200 measured frames; 9 large cases.
  This addresses the wider system-memory variation in the first sweep.
- Tables report medians of per-process means. GPU brackets are the min/max of
  those process means, not individual-frame extrema. All timing units are us.

Timing interpretation:
Three GPU timestamps bracket the upload calls, draw start and draw end. Draw GPU
below excludes preceding copies. Raw GPU span includes uploads and drawing;
OpenGL can also include command-feed/CPU gaps because it submits implicitly.
Consequently, raw GPU span is not treated as a directly comparable upload engine
measurement. CPU upload measures SetVertexBufferData + SetIndexBufferData calls.
Wall time includes frame acquisition, uploads, draws, presentation and final drain.
Queries are read after the final drain; there are no per-frame query waits.
The small hidden-window wall times include different backend/driver overheads and
should not be used as a general API ranking or an estimate of game frame rates.

The initial frame-slot probe observed both Vulkan and DX12 cycling through slots
0, 1 and 2 (mask 0x7). It did not observe DX12 collapsing to a single slot. A
separate control waits for completion after every frame on every backend to remove
cross-frame overlap; this measures latency including drain overhead, not throughput.

What the implementations did at the time of this comparison:
- Original Vulkan draws vertex/index data from host-visible system memory.
- DX12 copies into DEFAULT-heap device-local buffers. Its persistently mapped
  upload ring is 8 MiB per frame. These 16/48 MiB vertex uploads exceed that ring,
  so they take the temporary committed-upload allocation path on every update.
  The index uploads still fit in the ring. This is an allocation-policy difference
  from the reusable Vulkan staging candidate, not an inherent DX12 limitation.
- OpenGL calls glBufferData for full updates; allocation and placement are managed
  by the driver. Device-local-like read performance is observed, not a queried
  guarantee about the physical memory placement of each OpenGL buffer.

Candidate findings (before implementation, after the resource recheck)
---------------------------------------------------------------------
1. Both device-local modes remove the large repeated-read penalty. Resident GPU
   time falls from about 1809 us to 48.5 us in the recheck, approximately 37x. Actual frame throughput
   improves less because CPU and presentation overhead remain.
2. The winner depends on workload size. At 16 MiB, staging takes 1729 us/frame
   versus BAR's 1866 us with one streaming draw, about 7% less time. Four draws
   remain effectively tied (1818 versus 1829 us). At 48 MiB, BAR wins: 5429 versus
   6513 us for one draw, and 5518 versus 6525 us for four draws. Its CPU upload
   time is also lower at 48 MiB. Staging is not universally the fastest option.
3. Small uploads still have a tradeoff: at 64 KiB, direct host writes cost about
   2.6 us CPU, BAR about 6.7 us, and staging about 3.7 us in the recheck. All three are small
   relative to this harness's frame overhead. The test does not establish a
   universal crossover size or justify a hard-coded size threshold.
4. Staging into device-local vertex/index buffers remains a reasonable general
   baseline for discrete GPUs because it uses the main device-local heap and can
   support larger workloads. At 128 MiB, staging takes 18.43 ms/frame versus
   27.08 ms for host memory with one streaming draw. Retain reusable staging and
   destination allocations. A mapped device-local path can be faster where it
   fits, but cannot be the only path: this machine's BAR heap is only 214 MiB.
   Three slots of 48 MiB vertices plus indices consume 162 MiB there; three slots
   at 128 MiB would need 432 MiB. The implementation above selects reusable staging.
5. The original CPU copy-on-write path reads old mapped bytes on partial updates.
   Merely moving that backing to BAR memory could introduce slow CPU reads; this
   benchmark measures full sequential writes, not that partial-update path.
6. Validate AMD/Intel discrete hardware and an integrated/UMA device before treating
   this single-machine result as a cross-platform default. These are synthetic
   vertex-fetch workloads, not a reproduction of the reporter's complete game.
   No PCIe traffic counters were measured, so no traffic reduction is claimed.

Memory-selection change
-----------------------
GetMemoryTypeIndex now distinguishes mandatory properties from preferred and
softly avoided properties. It filters memoryTypeBits and required flags first,
maximizes the number of preferred matches, then minimizes avoided matches, and
preserves driver order for ties. Existing callers with no preferences keep their
current choice. The buffer allocation helpers accept the same optional preferences.
This permits explicit policies for device-local destinations, mappable GPU memory,
host staging and cached readback instead of one global preference for all callers.
The property-based overload supports deterministic tests without a GPU. Tests
cover compatibility, required properties, ranked preferences, unavailable preferred
types, UMA fallback, ties, no match, and memory type bit 31.
Preference fallback selects another compatible type when a preferred type is
absent. Allocation failure/budget fallback is a separate concern; this change does
not introduce a VRAM budget manager or automatic eviction.
The implemented production policy uses DEVICE_LOCAL destinations with a soft
preference against HOST_VISIBLE, and coherent host staging with a soft preference
against DEVICE_LOCAL. Both still accept compatible UMA memory types.
